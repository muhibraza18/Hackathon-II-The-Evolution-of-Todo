# Constitution: Todo Evolution - Phase I (In-Memory CLI Todo App)

## 1. Project Identity

**Project Name:** Todo Evolution - Phase I (In-Memory CLI Todo App)

**Scope:** A command-line interface (CLI) todo application using in-memory storage (list of dictionaries) only. No file persistence, databases, or external storage systems.

**Development Paradigm:** Strictly spec-driven development using Spec-Kit Plus methodology with automated code generation by Claude Code agents.

---

## 2. Core Principles

### 2.1 Spec-Driven Development
- All development MUST begin with a written specification
- Specifications SHALL be stored in `specs/` directory
- All specification iterations MUST be archived in `specs/history/`
- Code SHALL NOT be written without prior specification approval

### 2.2 Agentic Workflow
- The development process MUST follow this sequence:
  1. **Spec**: Write comprehensive specification
  2. **Plan**: Break specification into implementation tasks
  3. **Implement**: Generate code via Claude Code agents and skills
  4. **Verify**: Test and validate implementation against specification
- Manual coding is PROHIBITED. All code MUST be generated by agents.

### 2.3 Code Quality Standards
- All Python code MUST be PEP8-compliant
- Code MUST be clean, readable, and well-documented
- Functions MUST have clear, descriptive names
- Functions SHALL be modular and follow single-responsibility principle

### 2.4 Environment Management
- UV MUST be used for Python environment management
- UV MUST be used for dependency management
- No other package managers (pip, conda, poetry, etc.) SHALL be used

### 2.5 Data Storage
- ONLY in-memory storage is permitted (list of dictionaries)
- File-based storage is PROHIBITED
- Database storage is PROHIBITED
- Data persists only during application runtime

---

## 3. Required Features

All features listed below MUST be fully implemented:

### 3.1 Add Task
- Accept task title (required)
- Accept task description (required)
- Validate that both fields are provided
- Assign unique ID to the task
- Set initial status to incomplete
- Add task to in-memory storage

### 3.2 List/View All Tasks
- Display all tasks in a user-friendly format
- For each task, display:
  - ID (numeric)
  - Title
  - Status (✓ for complete, ☐ for incomplete)
  - Description
- Format output for readability

### 3.3 Update Task
- Accept task ID (required)
- Accept updated title (optional)
- Accept updated description (optional)
- At least one field (title or description) must be updated
- Validate that task ID exists
- Update the specified fields

### 3.4 Delete Task
- Accept task ID (required)
- Validate that task ID exists
- Remove task from in-memory storage
- Confirm deletion to user

### 3.5 Toggle Task Status
- Accept task ID (required)
- Validate that task ID exists
- Toggle status between complete and incomplete
- Display updated status to user

## 5. Development Workflow

### 5.1 Specification Phase
1. Create or update specification in `specs/`
2. Use spec-writer agent to create detailed specs
3. Archive previous version to `specs/history/`
4. Review and approve specification

### 5.2 Planning Phase
1. Use spec-planner agent to break spec into tasks
2. Generate implementation plan
3. Review and approve plan

### 5.3 Implementation Phase
1. Use python-implementer agent to generate code
2. Follow the implementation plan strictly
3. Ensure PEP8 compliance
4. Add docstrings where necessary

### 5.4 Verification Phase
1. Test each feature against specification
2. Verify PEP8 compliance
3. Confirm all requirements met
4. If verification fails, return to implementation phase

## 6. Technical Constraints

### 6.1 Python Version
- Minimum Python version: 3.8
- Target Python version: 3.11 or newer

### 6.2 Dependencies
- Only standard library modules are preferred
- If external dependencies are needed:
  - Document in pyproject.toml
  - Justify necessity in specification
  - Keep minimal set

### 6.3 Storage Architecture
```python
# In-memory storage structure
tasks = [
    {
        "id": 1,
        "title": "Task title",
        "description": "Task description",
        "complete": False
    },
    # ... more tasks
]
```
- ID MUST be unique (auto-incrementing integer)
- Title MUST be string, non-empty
- Description MUST be string, non-empty
- Complete MUST be boolean

## 7. User Interface Requirements

### 7.1 CLI Design
- Use clear, intuitive commands
- Provide help text for each command
- Display error messages for invalid input
- Confirm successful operations

### 7.2 Command Structure
Example commands (exact format to be defined in specification):
- `add "Task Title" "Task Description"`
- `list`
- `update <id> --title "New Title" --description "New Description"`
- `delete <id>`
- `complete <id>`
- `uncomplete <id>`

### 7.3 Output Format
- Tasks MUST be displayed in a tabular or list format
- Status MUST use ✓ or ☐ symbols
- Truncate long descriptions if necessary
- Show total task count
